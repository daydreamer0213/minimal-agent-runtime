# 架构设计题：详细讲解

> 本文档记录每道题的答案和解题思路。
>
> 当前进度：全部 10 题已完成。

## 模块一：Context / Performance

### 第 1 题

**问题：**

大模型面对第一轮长窗口或多模态输入时，第一个字会显著变慢。有什么快速、低成本、用户体验也不差的方案？如何从 5～10 秒稳定压缩到 2 秒？

#### 答案

首 token 延迟会影响用户对 Agent 响应速度的感受，可以从两个方向解决。

##### 1. 尽快提供真实反馈

请求到达后，通过 SSE 流式传输，持续向前端发送 Agent 的执行状态，例如“正在解析附件”“正在确认设备型号”“正在检索保修条款”。

如果模型已经产生了执行计划、推理摘要或工具调用进度，也可以同步展示。用户能够较早看到任务正在推进。

##### 2. 压缩真实首字延迟

长文件、图片和音频在上传阶段提前完成解析、切分和索引，并缓存处理结果。用户提问后，系统先识别问题中的指代，再检索相关内容，只把问题和必要证据交给大模型。

同时，可以并行执行意图识别、检索等轻量任务，为交互请求设置较高的排队优先级，并限制单次进入模型的内容长度。

对于已经完成基础解析的资料，可以把“用户发送问题到模型开始输出有效内容”控制在两秒左右。首次上传超大文件时，上传和解析时间需要单独计算。

通过真实进度反馈和实际性能优化的配合，可以同时改善等待过程，并尽可能压缩首字延迟。

#### 解题思路

看到这个问题时，我首先想到的是 SSE 流式传输。

SSE 可以理解为服务器和前端之间保持一条持续连接。服务器产生一条新消息，就可以立即发送一条，不必等整个回答完成后再一次性返回。

Agent 执行任务时会经历多个步骤，例如解析附件、检索资料、调用工具和生成回答。即使最终答案还没有产生，Runtime 也可以把这些真实状态发送给前端：

```text
收到用户请求
    ↓
正在解析附件
    ↓
正在确认设备型号
    ↓
正在检索保修条款
    ↓
模型开始生成回答
```

如果模型本身已经返回了执行计划、推理摘要或工具调用信息，也可以通过同一条连接展示。Codex 一类产品中看到的“思考”或任务进度，就可能来自这类模型输出和运行状态。

这个方案实现简单，额外计算成本也比较低，所以适合作为第一层优化。

继续分析后会发现，SSE 解决的主要是等待过程缺少反馈的问题。模型如果还在读取十几万 token 的上下文，或者系统还在处理几十张图片，最终答案仍然要等待 5～10 秒。SSE 可以更早传递进度，但没有减少这些计算。

因此还要继续解决真实首字延迟。

首字产生前的耗时可以大致拆成四段：

```text
文件上传和解析
        ↓
请求排队
        ↓
模型读取输入
        ↓
生成第一个 token
```

先记录每一段的耗时，才能知道优化重点在哪里。长窗口通常会增加模型读取输入的时间；扫描件、图片和音频还会增加解析时间；高峰期则可能主要慢在排队。

确定耗时来源后，可以从三个方面继续优化。

##### 第一，把可以提前做的工作放到上传阶段

用户选择文件后，系统就可以开始上传和解析，不必等到用户正式发送问题。

文档可以提前完成文字提取、切分和索引；图片可以提前识别文字和主要内容；音频可以提前转成文字。处理结果按文件保存，同一份资料后续不再重复解析。

这种做法的成本比较低，因为一次处理结果可以被后续多轮提问复用。

##### 第二，减少真正进入大模型的内容

用户提出具体问题时，大模型通常不需要阅读全部资料。

例如用户问“这台设备的保修期还有多久”，系统先从当前对话中确定“这台设备”的型号，再用型号、购买日期和保修期等信息检索相关材料。

最终交给大模型的内容可以压缩成：

```text
用户问题
+ 已确认的设备型号
+ 购买日期
+ 对应的保修条款
+ 少量必要的历史对话
```

模型需要读取的内容减少后，首字时间和 token 成本都会下降。

这里还要考虑检索失败的情况。证据足够时直接回答；证据不足时补查相邻段落或相关文件；无法确定设备型号时，再向用户确认。这样可以保留快路径，同时避免因为检索范围太小而答错。

##### 第三，缩短请求的关键路径

有些任务可以同时执行，例如附件解析、关键词提取和部分检索，没有必要全部串行等待。

交互请求还可以设置更高的排队优先级，避免被耗时较长的后台任务阻塞。简单的意图识别和检索，也可以交给速度更快、成本更低的小模型或规则完成，把大模型留在最后负责理解证据和组织答案。

最后还要明确“两秒”的统计范围。

如果文件已经完成基础解析，可以把“用户点击发送到模型开始输出有效内容”的 P95 延迟控制在两秒左右。P95 的意思是，一百次请求中至少有九十五次达到这个目标，比只看平均时间更能说明系统是否稳定。

如果用户第一次上传的是超大扫描件、长视频或大量图片，仅上传和解析就可能超过两秒。这种情况需要单独计算，并通过 SSE 展示真实进度。

最终，SSE 负责尽早传递真实进度；预处理、减少输入、并行执行和请求调度负责缩短真实延迟。两个方向配合，才有机会在控制成本的同时，把已解析资料的首字延迟稳定压缩到两秒左右。

### 第 2 题

**问题：**

一个 Session 连续聊了 200 轮，Context 快爆了。你会怎么做压缩？如何确保压缩后的对话仍然流畅？

#### 答案

对话接近 Context 上限后，既要释放空间，也要保住当前目标、用户要求和最新决策。我的方案分成三个方向。

##### 1. 按内容价值分层处理

先判断每部分内容对后续任务还有什么作用，再选择保留方式：

```text
用户要求、当前目标、限制和完成标准
→ 整理成独立的任务状态

最近几轮对话
→ 保留原文

工具输出、代码生成过程和重复排查记录
→ 只保留结果和关键依据

已经结束或失效的旧计划
→ 压缩成阶段结论，并标记当前状态

更早的完整对话
→ 移出当前 Context，需要时再检索
```

其中，用户仍然有效的要求、最新决定、当前进度和未解决问题需要单独保存，不能埋在一段大摘要里。

##### 2. 采用渐进式压缩

长工具调用结束后，及时把过程压成结果；一个任务阶段结束后，生成阶段总结；当旧总结积累到一定规模，或者 Context 接近预留上限时，再合并早期总结。

这样可以逐步释放空间，同时避免每轮都做压缩，增加额外延迟。

##### 3. 每轮重新组装必要上下文

每次调用模型时，提供三部分内容：

```text
当前任务状态
+ 最近几轮原文
+ 与本轮问题相关的历史记录
```

如果新决定修改了旧决定，当前状态只使用最新决定；旧决定保留为“已废弃”记录，并注明改变的时间和原因。

通过分层保存、渐进压缩和按需召回，可以释放 Context 空间，同时保持任务状态和对话衔接。

#### 解题思路

看到“200 轮对话，Context 快爆了”，我首先想到的是删除最早的消息，或者把全部历史压成一份摘要。

这种方案实现简单，也能快速腾出空间。但继续分析后会发现，消息的时间顺序不能直接代表它的重要程度。

例如，用户可能在第 10 轮提出“不要修改数据库”，这个要求到了第 200 轮仍然有效；而第 190 轮产生的几千行日志，问题解决后可能只需要保留一句结论。按照时间删除，很容易删掉仍然有效的要求，却留下体积很大的工作过程。

因此，压缩前要先判断每类内容的作用。

编程、检索和工具调用过程中会产生大量临时信息，例如完整日志、重复报错、代码生成过程和失败尝试。这些内容占用空间最多，任务完成后的价值通常较低，可以优先压成结果：

```text
压缩前：
多轮报错信息
+ 三次失败尝试
+ 大段工具输出
+ 最终修复过程

压缩后：
连接未正确释放导致登录超时；
修复已完成；
相关测试通过。
```

接下来需要处理旧的目标、计划和决定。它们的价值高于工具输出，但项目状态可能已经变化。

例如，第 30 轮决定使用方案 A，第 150 轮根据新的预算改成方案 B。当前 Context 中不能同时把 A 和 B 当成有效决定，否则模型后续可能随机选择其中一个。

处理方式是更新状态：

```text
当前决定：使用方案 B
旧决定：方案 A，已废弃
变更原因：预算下降
变更时间：第 150 轮
```

旧决定仍然保留，因为以后可能需要解释“为什么改成方案 B”；但它不会继续参与当前任务的执行。

继续往下思考，还会遇到一个问题：如果把所有重要内容都写进一段摘要，模型仍然可能忽略其中的用户要求。

因此需要把当前任务状态独立出来，固定保存以下内容：

```text
当前目标
用户仍然有效的要求
限制条件
完成标准
最新决定
当前进度
未解决问题
```

这份任务状态会在每次规划下一步时重新提供给模型。模型只需要根据当前状态决定下一步做什么，不需要从几百轮摘要中重新判断任务进行到了哪里。

确定了压缩内容后，还要考虑什么时候压缩。

每轮对话后都做一次压缩，内容变化小，却会不断增加模型调用和等待时间；一直等到 Context 快满时再一次压缩，又容易在短时间内处理大量信息，遗漏重要细节。

因此更合适的是两类触发方式：

```text
事件触发：
工具调用结束
任务阶段完成
一个问题已经解决

容量触发：
Context 接近预留上限
旧阶段总结积累过多
```

这种方式仍然是渐进式压缩，但压缩频率不会过高。

最后要检查压缩后的对话能不能自然衔接。

用户说“继续”“就用刚才那个方案”时，需要最近几轮原文才能理解指代；模型执行长程任务时，需要独立的任务状态；用户重新提到半个月前的问题时，需要从完整历史中检索相关记录。

所以每轮 Context 应当由三层内容组成：

```text
最近原文：保证当前对话自然衔接
任务状态：保证目标和进度不会丢失
相关历史：需要时从完整记录中检索
```

压缩完成后，还要检查用户要求、最新决定和未解决问题是否都进入了任务状态，并为阶段总结保留原始记录位置。摘要出现疑问时，系统可以回查原文，不需要完全依赖压缩后的内容。

最终，每轮对话只携带当前真正需要的信息：最近几轮原文负责衔接对话，任务状态负责维持目标和进度，完整历史则留在 Context 之外，需要时再检索。这样既能腾出足够的上下文空间，也能让模型自然地接着前面的任务继续工作。

## 模块二：Memory

### 第 1 题

**问题：**

和聊天 Agent 熟悉半个月后，用户问了一个以前问过的问题。Agent 如何做 Memory 召回更合理？

#### 答案

Memory 召回的目标，是恢复这个话题的最新状态，帮助用户接着上次的条件继续讨论，同时避免把半个月前的信息直接当成当前事实。可以从三个方向处理。

##### 1. 召回与当前话题有关的完整记录

系统先判断用户当前在问哪个话题，再检索这个话题的相关记忆，包括最初的问题、后来增加的要求、否定过的方案、条件变化和最终结果。

例如用户再次询问笔记本电脑，需要同时找回预算、用途、重量要求、排除过的型号，以及用户后来是否已经购买。

##### 2. 整理出这个话题的最新状态

召回结果按时间顺序和信息来源整理。最新的明确决定作为当前状态，旧决定标记为“已更新”或“已废弃”，继续保留变更原因。

例如：

```text
当前预算：12000 元
主要用途：编程和视频剪辑
重量要求：1.5 千克以内
旧预算：8000 元，已更新
购买状态：尚未确认
```

最终交给模型的是整理后的当前状态，不是多条互相冲突的历史记录。

##### 3. 确认可能已经变化的重要条件

长期稳定的偏好，例如喜欢轻薄、习惯 Windows，可以自然带入回答。

预算、所在地、截止时间和任务是否已经完成，半个月后都有可能发生变化。如果这些信息会明显影响答案，Agent 应先向用户确认：

> “你上次把预算调整到 12000 元，还增加了视频剪辑和 1.5 千克以内的要求。这次仍按这些条件推荐吗？”

用户确认后，再结合当前信息重新回答。记忆可靠性不足时，直接询问用户，不根据模糊记录生成确定结论。

#### 解题思路

看到“用户再次问了一个以前问过的问题”，我首先想到的是做相似度检索：用当前问题搜索历史 Memory，找到半个月前的相似问答。

这种做法能够识别“用户以前问过”，实现也比较简单。但找到原来的问题和答案后，会出现第一个缺口：半个月内可能产生了新的条件。

例如用户最初询问笔记本时预算是 8000 元，后来增加了视频剪辑需求，又把预算提高到 12000 元。如果系统只召回最初的问答，就会根据已经失效的预算重新推荐。

因此，召回单位应该从“某一条相似消息”扩大到“与当前问题有关的整个话题”。系统需要找到这个话题的起点，也要找到后续补充、修改、否定和任务结果。

完成话题召回后，还会遇到第二个问题：检索结果里可能同时存在多种互相冲突的条件。

```text
第 1 天：预算 8000 元
第 8 天：增加视频剪辑需求
第 10 天：预算调整到 12000 元
```

如果把这些记录原样交给模型，模型需要自己判断哪个预算仍然有效，回答结果可能不稳定。因此，Memory 层要先整理状态：12000 元作为当前预算，8000 元保留为已经失效的旧记录。

整理出最新状态后，还不能直接使用，因为这份“最新状态”也是半个月前留下的。预算可能再次变化，用户也可能已经买完电脑，不再处于选购阶段。

这就引出了第三个方向：根据变化可能性和错误影响决定是否确认。

长期稳定、记忆来源明确的偏好，可以直接使用。容易变化且会显著影响回答的信息，需要先确认。记忆比较模糊、来源不可靠或存在冲突时，重新询问用户更稳妥。

最后还要控制召回内容的数量。模型只需要看到本次回答相关的当前状态和必要的变更记录。完整的历史检索过程保留在 Memory 系统中，不需要全部放进当前 Context，也不需要全部展示给用户。这样既利用了长期记忆，又不会让旧记录干扰当前回答。

### 第 2 题

**问题：**

你理解的 Agent Memory 经典框架是什么？它的发展趋势是什么，最头部的玩家在怎么做？

#### 答案

Agent Memory 可以从三个方面理解：经典框架解决“记什么、怎样使用”，发展趋势解决“正在向哪里演进”，头部玩家则代表不同的落地方向。

##### 1. 经典框架

从内容类型看，Agent Memory 通常分成四类：

```text
工作记忆：当前任务的目标、进度和临时结果
情景记忆：过去发生过的对话、操作和任务经历
语义记忆：用户偏好、项目事实等相对稳定的信息
程序记忆：完成某类任务的方法、规则和经验
```

不同类型的记忆有不同的使用方式。工作记忆在执行当前任务时持续使用；情景记忆在遇到相似经历时召回；语义记忆在相关任务中长期生效；程序记忆在执行对应任务时使用。

一套完整的 Memory 系统还需要管理记忆的生命周期：

```text
选择性写入
→ 分类和分作用域保存
→ 按当前任务召回
→ 合并、更新和处理冲突
→ 过期、归档或删除
```

记忆类型决定保存什么，生命周期决定这些记忆怎样长期维护。

##### 2. 发展趋势

早期方案通常保存聊天记录，再通过向量相似度查找相关片段。现在的发展重点主要有五个：

- 写入时筛选真正值得长期保存的信息；
- 召回时同时考虑相关性、时间、来源和当前状态；
- 分开管理用户、Session、项目、Agent 和组织记忆；
- 在后台完成去重、合并、冲突处理和过期清理；
- 允许用户查看、修改、删除、暂停或导出记忆。

Memory 正在从聊天记录检索，发展成能够持续更新、区分作用域并接受用户管理的状态系统。

##### 3. 头部玩家及各自方向

| 玩家 | 主要方向 |
|---|---|
| ChatGPT | 个人长期记忆、历史对话引用、项目级记忆和用户控制 |
| Claude | 分类记忆、项目独立记忆、过去聊天搜索和记忆来源追溯 |
| Gemini | 结合历史对话和 Google 应用数据，形成更完整的个人信息 |
| LangGraph | 管理 Session 内的短期状态、跨 Session 的长期记忆和记忆作用域 |
| Letta | 让 Agent 维护常驻 Memory Block，并按信息规模接入文件和外部存储 |
| Mem0 | 将记忆提取、去重、冲突处理、召回、更新和删除做成独立服务 |

ChatGPT、Claude 和 Gemini 主要改善用户的跨对话体验；LangGraph 和 Letta 主要解决开发 Agent 时的状态管理；Mem0 主要提供可复用的 Memory 基础设施。

#### 解题思路

看到“Agent Memory 经典框架”，我首先想到的是认知科学中常见的四类记忆：工作记忆、情景记忆、语义记忆和程序记忆。

这四类记忆可以解释 Agent 应该保存哪些内容，也能解释它们分别在什么时候使用。

例如，当前任务的目标和进度需要每一步都能读取，所以属于工作记忆；用户过去遇到过的一次故障，只在再次出现类似问题时才需要召回，所以属于情景记忆；用户偏好使用中文，可能在很多任务中持续生效，所以属于语义记忆；完成代码审查的检查步骤，只在执行代码审查时使用，所以属于程序记忆。

继续考虑后会发现，只回答记忆分类还不够。分类只能说明“记什么”，没有说明信息怎样进入 Memory、怎样被找回来，以及发生变化后怎样更新。

因此还需要加入记忆生命周期：

```text
写入 → 存储 → 召回 → 更新 → 遗忘
```

先看写入阶段。

最简单的方案是把每次对话都保存下来。这样不会主动遗漏信息，但长期使用后会积累大量临时内容、重复信息和未经确认的推测。

长期记忆的调用会影响模型后续判断。少记一条信息时，Agent 通常还可以重新询问用户；错误记忆被反复召回，会让 Agent 持续给出错误回答。因此，写入长期记忆需要经过筛选。

比较适合长期保存的内容包括：

- 用户明确要求记住的信息；
- 长期稳定的偏好和事实；
- 会影响后续任务的重要决定；
- 已经验证的成功经验和失败教训。

每条记忆还要记录所属用户或项目、写入时间、信息来源、可信程度和当前状态。后续出现新信息时，系统才能判断应该新增一条记忆，还是更新已有状态。

完成写入设计后，下一个问题是怎样召回。

最容易想到的是向量相似度检索，也就是从历史记录中找到与当前问题意思相近的内容。它可以解决基本的相关性问题，但还会遇到三种情况：

```text
内容相似，但对当前任务不重要
内容曾经正确，现在已经过期
新旧两条记忆互相冲突
```

因此召回时还需要考虑时间、来源、可信度和有效状态。复杂场景可以加入关键词检索、结构化字段或关系图，再对候选记忆进行排序，最后只把少量可靠内容交给模型。

接着还要考虑记忆的作用范围。

用户的表达偏好可以跨多个 Session 使用；某个项目的技术决定只能在对应项目中使用；当前任务的中间结果只属于当前 Session；公司的操作规范可能需要在多个 Agent 之间共享。

所以 Memory 需要区分不同作用域：

```text
Session 记忆
用户记忆
项目记忆
Agent 记忆
组织记忆
```

作用域可以减少无关信息的干扰，也能防止不同用户和项目之间发生记忆串用。

长期运行后，Memory 还会不断增加。因此，系统需要在后台合并重复记忆、更新已经变化的状态、清理过期内容。用户也应该知道系统记住了什么，并能够修改、删除、暂停或导出自己的记忆。

最后，题目还问“头部玩家在怎么做”。我会把前面的框架拿来对照具体产品，看每家重点解决哪一部分。

先看面向普通用户的产品。

ChatGPT 重点处理个人长期记忆和历史对话的延续，同时加入项目级记忆。用户可以查看、修改或删除记忆，也可以使用不参与记忆的临时对话。

Claude 同样在做跨对话记忆，但更强调项目之间的隔离、记忆条目的分类管理，以及引用过去聊天时能够找到来源。

Gemini 的方向更接近个人信息整合。它除了参考历史聊天，还可以结合 Gmail、日历、搜索等 Google 应用中的信息来完成个性化任务。

再看开发 Agent 时使用的框架。

LangGraph 把当前 Session 的状态和跨 Session 的长期记忆分开管理。它更关注开发者怎样定义记忆属于哪个用户、项目或任务，以及在什么时候写入和召回。

Letta 更强调 Agent 自己管理记忆。重要信息可以放在始终可见的 Memory Block 中，大量资料则放入文件、归档记忆或外部检索系统。

最后是独立的 Memory 服务。Mem0 把对话中的重要信息自动提取出来，并负责去重、处理冲突、搜索、更新和删除。它解决的是不同 Agent 重复建设 Memory 系统的问题。

把这些玩家放在一起看，可以发现它们分别在补 Memory 的不同部分：ChatGPT、Claude 和 Gemini 关注用户怎样使用和控制记忆；LangGraph 和 Letta 关注 Agent 怎样组织和调用记忆；Mem0 关注记忆服务本身怎样稳定运行。

这时，发展趋势也比较清楚了：Memory 已经不再停留在“保存聊天并做相似搜索”，而是逐步覆盖选择性写入、作用域管理、状态更新、冲突处理和用户控制。

## 模块三：Task

### 第 1 题

**问题：**

对于长程任务，大模型执行一段时间可能会忘掉目标。你知道哪些解决方案？有什么优缺点？

#### 答案

长程任务执行时间越长，局部问题、工具输出和中间结果越容易淹没总目标。解决思路是把目标和任务状态放在模型之外持续保存，再用动态规划和结果检查保证执行方向。

常见方案及优缺点如下：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 重复注入目标 | 实现简单，可以提醒模型最终要做什么 | 不记录当前进度，反复占用上下文 |
| 外部任务状态 | 可以保存目标、限制、进度和待办，支持中断恢复 | 状态更新错误会持续误导后续执行 |
| 分层计划 | 把长任务拆成阶段和步骤，降低单次规划难度 | 早期计划可能随着新信息失效 |
| 阶段检查或独立监督 | 能发现任务是否偏离，以及结果是否真的完成 | 增加模型调用和执行成本，监督模型也可能出错 |
| 固定工作流或状态机 | 步骤清晰、结果稳定，适合硬性流程 | 灵活性较低，不适合路径未知的探索任务 |

实际设计中，我会以外部任务状态为主线，组合四部分：

```text
固定目标卡
+ 持续更新的任务状态
+ 可以调整的分层计划
+ 关键步骤的结果检查
```

目标卡保存用户目标、限制和完成标准；任务状态记录当前进度、已完成步骤、待办和阻塞；模型每次只规划下一段可验证的工作；执行结果通过工具或 Runtime 检查后，再更新任务状态。

程序能够判断的硬限制，例如“不能新增依赖”“必须运行测试”，由 Runtime 单独校验。这样可以减少模型偏离目标的概率，也能在任务中断或上下文压缩后继续执行。

#### 解题思路

看到“大模型执行一段时间后忘掉目标”，我最先想到的是在每轮调用时重新加入用户的原始目标。

这个办法实现起来很简单。例如任务目标是“完成登录模块并通过全部测试”，系统可以在每次请求模型时都把这句话放在提示词前面。即使中间产生了大量代码和日志，模型仍然能够看到最终目标。

继续分析后会发现，只重复目标还不够。

模型虽然知道“最终要完成登录模块”，却不知道当前已经修改了哪些文件、哪些测试已经通过、还有什么问题没有解决。它可能重复已经完成的工作，也可能误以为某个步骤已经结束。

因此需要把目标、限制、完成标准和当前进度整理成一份独立的任务状态，保存在 Runtime 或数据库中：

```text
目标：完成登录模块
限制：不能新增第三方依赖
完成标准：单元测试和集成测试全部通过
当前进度：接口已经完成，前端页面待修改
已完成：登录接口、密码校验
待处理：错误提示、集成测试
阻塞问题：测试环境暂时不可用
```

每次规划下一步时，系统重新把这份任务状态提供给模型。模型只需要根据当前状态决定下一步做什么，不需要一直从完整对话中寻找总目标和历史进度。

外部任务状态解决了“记不住”的问题，但又带来一个新风险：状态本身可能不准确。

模型可能在输出中说“测试已经通过”，实际测试命令却没有运行；也可能说“文件已经修改”，工具调用却执行失败。如果 Runtime 直接相信模型的文字，就会把错误结果写进任务状态，后面的执行都会建立在错误基础上。

所以状态更新需要以真实执行结果为依据：

```text
模型提出下一步
→ Runtime 执行工具
→ 检查工具返回结果
→ 确认成功后更新任务状态
```

能够自动判断的要求，可以交给程序检查。例如测试命令是否执行、退出码是否为零、是否新增了依赖、目标文件是否存在。这些硬性要求比模型自查更稳定。

解决状态准确性后，还要考虑计划会不会过期。

长程任务开始时可以生成总体计划，但执行过程中经常会发现新的限制。例如原计划准备修改数据库，后来发现用户没有数据库权限；原计划准备使用某个依赖，后来发现项目不允许新增依赖。继续执行旧计划会让任务偏离实际情况。

因此，总目标、用户限制和完成标准保持稳定，执行计划允许根据新信息调整。

比较合适的计划结构是：

```text
总目标
  ├─ 当前阶段
  │    ├─ 下一步操作
  │    └─ 验证方式
  └─ 后续阶段
```

模型每次重点规划一个可以验证的下一步。完成后根据真实结果更新任务状态，再决定是否继续原计划或重新规划。

接下来还要考虑：即使每一步都执行成功，任务整体也可能走偏。

例如模型完成了很多代码修改，但忽略了用户最初要求的兼容性；或者所有局部测试都通过，最终功能仍然不符合验收标准。因此，在阶段结束和任务结束时，需要重新对照目标卡：

```text
当前结果是否满足用户目标
是否违反任何限制
完成标准是否全部验证
是否还有未解决问题
```

对于路径固定的任务，例如审批、数据导入和发布流程，可以进一步使用状态机，把允许执行的步骤和跳转条件写死。这种方式最稳定，但探索性任务需要根据新发现调整路径，不适合完全固定。

最后形成的执行方式是：目标卡负责保持方向，任务状态负责记录进度，动态计划负责决定下一步，Runtime 检查负责确认结果。模型可以专注当前操作，同时由外部系统持续保证整个任务没有偏离。

### 第 2 题

**问题：**

用户给 Agent 下达任务：

> 每天早上 9 点，根据昨天聊天情况做复盘总结。

你会怎么设计？

#### 答案

这是一个跨时间执行的周期任务。模型负责理解聊天和生成复盘，Runtime 负责定时触发、权限检查、状态保存、失败重试和结果通知。

整体流程是：

```text
用户创建定时任务
→ 每天 9 点触发一次独立运行
→ 读取昨天的授权聊天
→ 生成并保存复盘
→ 通知用户查看结果
```

具体分成四部分设计。

##### 1. 保存任务配置

创建任务时，需要让用户明确以下内容：

```text
执行时间和时区
允许读取的 Session 或项目
复盘内容和格式
结果保存位置
通知方式
没有聊天时是否发送空结果
```

读取范围需要由用户主动选择。例如只读取“学习项目”中的聊天，系统不能默认扫描用户的全部 Session。

##### 2. 独立调度和执行

调度器按照用户时区每天早上 9 点创建一个新的执行实例。原来的 Session 不需要一直保持运行。

“昨天”按用户当地时间的自然日计算。例如上海时区 7 月 28 日 9 点执行，应读取 7 月 27 日 0 点到 7 月 28 日 0 点之前的聊天。

每次运行使用“定时任务编号 + 日期”作为唯一标识，防止同一天重复生成复盘。

##### 3. 读取聊天并生成复盘

执行前重新检查用户权限，只读取当前仍然有权访问的 Session。

聊天较少时可以直接总结；聊天较多时先分别整理每个 Session，再合并成当天复盘：

```text
各 Session 的聊天记录
→ 提取完成事项、重要决定、问题和待办
→ 合并重复内容
→ 生成每日复盘
```

总结需要区分聊天中的明确事实和模型的推测，避免把讨论中的猜测写成已经完成的事项。

##### 4. 保存结果并处理失败

复盘生成后先保存，再发送通知。这样通知失败时只需要重新通知，不必重新调用模型生成一遍。

临时错误可以自动重试；系统在 9 点不可用时，恢复后补跑遗漏任务；多次失败后再通知用户处理。每次执行都保存运行状态，方便查看任务是否成功、失败或正在重试。

#### 解题思路

看到“每天早上 9 点”，我首先想到的是把这条要求保存在当前 Session 中，让模型到时间后自动执行。

但模型本身没有持续运行的计时能力。当前对话关闭后，模型不会一直等到第二天早上；服务重启或 Session 结束后，这条任务也可能失去执行状态。

因此需要把它创建成一个独立的定时任务，交给 Runtime 中的调度器管理。Runtime 可以理解为负责真正运行 Agent 任务的后台系统，它保存任务配置，并在指定时间创建一次新的执行实例。

解决触发问题后，下一个问题是调度器需要保存哪些信息。

只保存“每天 9 点执行”还不够，因为系统不知道用户在哪个时区，也不知道应该读取哪些聊天。用户可能只想复盘某个学习项目，如果系统读取全部 Session，会带来隐私问题，也可能把无关聊天混进总结。

所以创建任务时，需要明确时间、时区、读取范围、复盘格式、保存位置和通知方式。读取范围可以是一个 Session、多个指定 Session，或者一个项目。

接下来要确定“昨天”的时间范围。

最容易想到的是从执行时间向前推 24 小时。但用户通常理解的“昨天”是当地时间的自然日。早上 9 点执行时，向前推 24 小时会得到前一天早上 9 点到当天早上 9 点，这会漏掉前一天早上的聊天，也会混入当天的内容。

因此要先将用户时区中的日期转换成明确范围：

```text
昨天 00:00
到
今天 00:00
```

确定时间和读取范围后，才进入总结阶段。

如果只有一个 Session、聊天内容也很少，可以直接交给模型总结。如果用户授权了多个 Session，或者一天内聊天很多，直接合并全部内容会增加输入长度，也容易让不同话题互相干扰。

这时可以先按 Session 分别整理：

```text
Session A → 完成事项、决定、问题、待办
Session B → 完成事项、决定、问题、待办
Session C → 完成事项、决定、问题、待办
```

然后再合并重复内容，生成最终的每日复盘。没有相关聊天时，可以根据用户创建任务时的设置，选择跳过通知或发送“昨天没有可复盘内容”。

总结生成后，还要考虑系统故障。

调度器可能因为网络抖动重复触发同一个任务。如果每次触发都直接生成复盘，用户可能收到两份结果，还会产生重复的模型调用成本。因此，每次运行需要一个唯一标识：

```text
定时任务编号 + 复盘日期
```

系统发现同一个标识已经成功完成时，就不再重复执行。

还可能出现另一种情况：复盘已经生成成功，但发送通知失败。如果生成和通知绑定在一起，重试时会再次调用模型。更合理的处理方式是先保存复盘结果，再单独发送通知。通知失败时，只重试通知。

最后还要重新检查权限。用户可能在创建任务后删除某个 Session、退出项目或撤销授权。每次执行都要根据当前权限读取数据，不能一直使用创建任务时的旧权限。

最终，各部分职责就明确了：调度器负责按时创建任务，权限系统决定可以读取什么，模型负责生成复盘，存储系统保存结果，通知系统负责把完成情况告诉用户。

## 模块四：Tool / Session Runtime

### 第 1 题

**问题：**

Agent 工具有同步和异步两类。异步工具不能让用户一直等，但结果依然重要。你会如何设计异步工具执行和完成通知？

#### 答案

异步工具的核心设计，是把用户当前请求、后台工具任务和结果通知拆成三个独立环节，并为每个环节保存状态。

整体流程是：

```text
Agent 发起工具调用
→ 创建后台任务并返回任务编号
→ Worker 执行工具
→ 保存工具结果
→ 必要时恢复 Agent 继续处理
→ 保存最终结果
→ 通知用户
```

具体分成四部分。

##### 1. 创建可持久化的后台任务

Agent 调用异步工具时，Runtime 创建一条任务记录，保存：

```text
任务编号
来源 Session 和 Agent 任务
工具名称和输入参数
当前目标和任务版本
唯一调用标识
创建时间和执行状态
```

创建成功后立即告诉用户“任务已转入后台”，并返回任务编号。用户可以继续聊天、关闭页面，也可以根据任务编号查询进度或取消任务。

##### 2. 后台执行并保存状态

Worker 从队列中领取任务，持续更新状态：

```text
等待执行
→ 正在运行
→ 成功 / 失败 / 已取消
```

临时网络错误可以自动重试；参数错误、权限错误等确定性问题直接标记失败。

队列消息可能重复投递，所以每次调用都要有唯一标识。Worker 执行前先检查该任务是否已有结果，避免工具重复执行、重复扣费或产生两份外部资源。

##### 3. 区分工具完成和 Agent 任务完成

有些工具完成后可以直接交付，例如图片生成；有些工具只返回中间材料，例如研究工具返回资料后，Agent 还需要整理成报告。

工具完成事件到达后，Runtime 先保存结果，再读取原任务的最新状态：

- 结果可以直接交付：生成最终结果消息；
- 还需要模型处理：创建一次新的 Agent 执行；
- 用户已经取消任务：保存结果，不再继续旧流程；
- 用户已经修改目标：根据最新要求决定是否继续使用该结果。

这样可以避免异步工具完成后，系统继续执行已经过期的计划。

##### 4. 保存结果后再通知用户

最终结果需要先持久保存，再发送通知。通知失败时只重试通知，不重新执行工具或模型。

用户仍在应用内时，可以通过 SSE 或 WebSocket 接收进度和完成事件；用户已经离开时，可以使用应用通知、邮件或其他授权渠道提醒。

外部通知只显示“任务已完成”或简短摘要。用户进入应用并通过权限检查后，再查看完整结果。

#### 解题思路

看到“异步工具不能让用户一直等”，我首先想到的是让当前请求保持连接，等工具完成后再通过 SSE 把结果发回来。

如果工具只运行几十秒，并且用户一直停留在页面，这种方式实现起来很直接。但异步工具可能运行几分钟甚至几小时，用户可能关闭页面，HTTP 连接也可能中断，服务进程还可能重启。任务执行不能依赖这条连接一直存在。

因此，用户请求和工具执行需要分开。

Agent 决定调用异步工具后，Runtime 先创建一条持久化任务记录，再把任务放入后台队列。持久化的意思是任务保存在数据库中，服务重启后仍然能够找到。

前端收到任务编号后就可以结束当前等待：

```text
任务已创建
编号：tool-job-123
状态：等待执行
```

用户可以继续聊天，也可以离开页面。之后查询任务编号，就能看到当前进度。

建立后台任务后，还会遇到任务重复执行的问题。

消息队列为了避免任务丢失，可能把同一条消息再次交给 Worker。例如 Worker 已经调用了付费图片生成接口，但在保存状态前发生网络中断；队列会认为任务没有完成，再投递一次。

如果没有去重，同一个请求可能生成两张图片、扣费两次。因此每次工具调用都需要唯一调用标识。Worker 执行前检查这个标识是否已经有结果，再决定是否真正调用外部工具。

接下来要保存任务状态。只记录“完成或未完成”还不够，因为用户需要知道任务正在等待、执行、重试，还是已经失败。

```text
queued：等待执行
running：正在运行
succeeded：执行成功
failed：执行失败
cancelled：用户取消
```

临时网络错误可以重试；输入参数错误或权限不足继续重试也不会成功，应直接记录失败原因并通知用户。

工具成功后，又会出现一个容易忽略的问题：工具完成不代表用户交代的任务已经完成。

例如，图片生成工具返回图片后，可以直接交付给用户；研究工具返回十篇资料后，用户真正需要的是一份整理完成的报告。

所以工具结果保存后，要根据原任务判断下一步：

```text
工具结果
├─ 可以直接交付 → 保存最终消息
└─ 还需要处理 → 恢复 Agent 继续执行
```

恢复 Agent 时需要读取最新任务状态。用户可能在等待期间补充了要求，也可能已经取消任务。如果系统只恢复几小时前保存的旧快照，就可能继续执行已经失效的计划。

最后考虑通知。

最直接的做法是工具完成后立即发送通知。但如果通知发送成功、结果保存失败，用户点击后会找不到内容；如果结果已经生成、通知失败，重新运行整个任务又会产生重复成本。

所以顺序应该固定为：

```text
保存工具结果
→ 完成必要的后续处理
→ 保存最终结果
→ 发送通知
```

通知拥有自己的发送状态和重试次数。它失败时只重试通知，已经完成的工具任务和模型处理不再重复执行。

最终，这套设计让三部分各自独立：后台任务保证工具能够持续执行，Agent 恢复机制负责完成剩余工作，通知系统负责把结果交付给用户。任何一个环节短暂失败，都不会让前面已经完成的工作丢失。

### 第 2 题

**问题：**

如果 Session State 为 `busy`，此时用户又发来新消息，或者异步工具完成事件也到达，Runtime 应该如何处理？

#### 答案

`busy` 表示当前有一个执行流程正在修改 Session，并不影响 Runtime 接收新事件。处理原则是：**事件先保存，按照类型决定优先级，Session 状态始终由一个执行流程顺序修改。**

整体流程是：

```text
新事件到达
→ 保存到 Session 事件队列
→ 判断事件类型和关联任务
→ 中断当前执行或等待安全位置
→ 由唯一执行者更新 Session State
→ 根据最新状态继续规划
```

具体分成四部分。

##### 1. 所有事件先保存

用户消息和异步工具事件到达后，先写入持久化事件队列，并记录：

```text
事件编号
事件类型
所属 Session
关联任务或工具编号
到达时间
状态版本
```

保存成功后立即回复用户，例如“补充要求已收到，将在当前步骤完成后应用”。即使服务重启，事件也不会丢失。

##### 2. 根据事件类型决定处理时机

| 事件类型 | 处理方式 |
|---|---|
| 停止、取消、权限撤销 | 请求中断当前执行，优先处理 |
| 修改目标、补充要求 | 保存后，在当前步骤结束的安全位置应用 |
| 查询进度 | 读取最近一次已保存的状态，不修改任务 |
| 无关的新任务 | 排队等待，或者创建新的 Session |
| 异步工具完成 | 保存结果并去重，再检查原任务状态 |

安全位置指一个步骤已经执行完、结果已经保存，Session State 处于完整状态的时刻。在这里应用新要求，可以减少状态只更新一半的问题。

##### 3. Session State 只允许一个执行流程修改

同一时间只有一个执行流程可以提交 Session State，这就是单写入者原则。

Runtime 可以为每个 Session 建立串行队列，并给状态添加版本号。旧执行流程提交结果时，如果发现状态版本已经变化，就不能直接覆盖新状态，需要重新读取后再处理。

##### 4. 异步结果根据原任务的最新状态处理

异步工具结果先根据工具任务编号保存并去重，然后检查原任务：

```text
原任务仍在等待结果
→ 恢复 Agent 继续执行

原任务已经取消
→ 保存结果，不再恢复任务

用户已经修改目标
→ 判断结果是否仍然有用，再重新规划

结果属于其他任务
→ 放入对应任务，不写入当前执行
```

这样可以保证新事件不会丢失，也能避免多个执行流程互相覆盖状态。

#### 解题思路

看到 Session 处于 `busy`，我最先想到的处理方式是拒绝后续消息，等当前任务完成后再允许用户发送。

这种方式实现简单，也不会出现两个流程同时修改状态。但用户可能发来“立即停止”“不要再发送邮件”这类紧急指令，直接拒绝会让当前任务继续产生不应该发生的副作用。异步工具结果也可能很昂贵，拒绝接收会导致结果丢失。

所以，新事件不能因为 Session 正忙就被丢弃。

接下来想到的是让新事件立即进入当前执行流程，直接修改 Session State。这样反馈速度快，但会产生并发问题。

例如当前流程刚读取到“生成普通报告”，用户同时补充“增加风险分析”。旧流程可能在用户要求写入后，又用自己手中的旧状态覆盖数据库，导致新要求消失。

异步工具事件也有同样的问题。搜索工具根据旧目标返回结果后，如果直接恢复任务，可能会继续执行用户已经取消的计划。

因此，需要先把事件可靠保存，再安排一个执行流程顺序处理。最直接的实现是为每个 Session 建立持久化事件队列：

```text
当前执行事件
用户补充要求
异步工具完成事件
进度查询
```

队列解决了事件不丢的问题，但只按到达顺序处理还不够。

用户的“增加一个章节”通常可以等当前步骤完成；“立即停止任务”需要尽快中断；进度查询只读取状态，不需要进入写入队列。事件必须先分类，再决定优先级和处理时机。

普通修改适合在安全位置生效。安全位置可以是模型一轮生成结束、工具调用完成，或者一个任务步骤已经保存结果之后。此时状态是完整的，可以先应用新要求，再规划下一步。

紧急停止可以提前发送中断信号。中断成功后，Runtime 仍要保存已经完成的部分，并把任务状态改成已取消，避免异步结果稍后到达时重新启动任务。

事件能够顺序处理后，还要防止旧执行结果覆盖新状态。

假设执行流程读取状态时版本号是 10，用户新要求写入后状态变成 11。旧流程提交结果时发现版本号已经变化，就不能再按照版本 10 直接覆盖，而要重新读取最新状态。

异步工具结果还需要带上原任务编号和唯一事件编号。任务编号用于判断结果属于哪个目标，事件编号用于防止同一个完成通知被处理两次。

例如 Session 正在生成报告，用户补充“增加风险分析”，同时搜索工具返回资料。Runtime 会先保存两件事，等当前步骤结束后应用新要求，再判断搜索结果能否支持风险分析。如果可以，就把它加入新计划；如果原任务已经取消，只保存资料，不再恢复执行。

最终，`busy` 只限制谁可以修改 Session State，不限制系统接收消息。事件队列保证信息不会丢，事件分类决定处理时机，单写入者和版本号保证状态不会被并发覆盖。

## 模块五：Agent Runtime 架构对比

### 第 1 题

**问题：**

Claude Code 的工具输出方式和国内 GLM、豆包等 OpenAI-compatible Function Calling 有什么不同？各自这样设计的优缺点是什么？

#### 答案

这道题比较的核心，是两种工具消息的组织方式不同：Claude 使用可组合的内容块，GLM、豆包常见的 OpenAI-compatible Chat Completions 使用独立的工具角色。

具体格式如下：

```text
Claude：
assistant 中产生 tool_use
→ Runtime 执行工具
→ user 中返回 tool_result

OpenAI-compatible：
assistant 中产生 tool_calls
→ Runtime 执行工具
→ tool 消息返回结果
```

##### 1. Claude：内容表达更灵活，Runtime 处理更复杂

Claude 把文本、图片和工具结果都组织成内容块。一次消息里可以组合多种内容，比较适合 Claude Code 这类经常读取文件、截图和终端输出的 Agent。

它的代价是协议处理更复杂。Runtime 不仅要关联调用 ID，还要保证 `tool_use` 和 `tool_result` 的顺序正确，并识别不同类型的内容块。

##### 2. OpenAI-compatible：角色更清楚，接入成本更低

OpenAI-compatible 使用独立的 `tool` 角色。查看日志时，可以直接区分用户输入、模型输出和工具结果，保存、调试和排查都比较直观。

这套格式已经被许多模型和 SDK 采用，所以接入 GLM、豆包等厂商时，基础代码可以复用。不过，所谓 compatible 通常只代表主要字段相似，不代表各家对并行调用、参数校验和多模态结果的支持完全一致。

常见的 Chat Completions 工具结果仍以文本或 JSON 为主。工具产生图片、PDF 等结果时，通常需要返回文件地址或文件 ID，再由系统单独读取。

##### 3. 实际架构：内部统一，外部适配

如果系统需要接入多个模型，我会在 Runtime 内部定义统一结构：

```text
ToolCall：调用哪个工具、参数是什么
ToolResult：对应哪次调用、是否成功、返回了什么内容
```

Claude、OpenAI、GLM 和豆包的协议先经过适配器转换成这个结构。这样更换模型时，只需要修改适配器，不需要重写整个工具系统。

OpenAI 新的 Responses API 也开始使用独立的调用项和结果项，并增强了文件、图片等内容的表达能力。这说明协议正在向更适合 Agent 的方向发展，但不能把这种新能力直接等同于所有厂商都支持的 OpenAI-compatible 格式。

#### 解题思路

看到这道题，我会先把两种工具调用记录放在一起比较。

OpenAI-compatible 的记录很容易理解：模型发出 `tool_calls`，工具通过独立的 `tool` 消息返回结果。第一感觉是它的角色划分更清楚，日志里谁说了什么一目了然。

Claude 的工具结果却放在 `user` 消息中，刚开始看会觉得角色有些奇怪。但继续看它的消息结构，会发现这里的 `user` 不一定代表真人，也可以表示模型外部提供的新内容。真正有价值的地方，是 `tool_result` 和文本、图片一样，都是可以组合的内容块。

因此，需要把两个问题分开：

```text
怎样区分消息来源？    → 角色设计
一条消息能携带什么？  → 内容设计
```

OpenAI-compatible 在第一个问题上更直观；Claude 在第二个问题上更灵活。不能简单地认为 Claude 因为使用 `user` 角色所以支持多模态，也不能认为独立的 `tool` 角色一定只能返回文本。

接下来要看这种差异对 Runtime 有什么影响。

普通业务工具大多返回 JSON，例如订单信息、天气数据和数据库查询结果。此时独立的 `tool` 消息已经够用，结构也比较容易保存和排查。

编码 Agent 的工具输出更复杂，可能同时包含文件内容、报错位置、截图和终端日志。Claude 的内容块能够更自然地表达这些结果，但 Runtime 也要处理更多内容类型和严格的消息顺序。

最后再考虑多模型接入。即使 GLM 和豆包都声称兼容 OpenAI，也不能假设它们的行为完全相同。与其让业务逻辑直接依赖某一家协议，更稳妥的做法是在 Runtime 内部统一 `ToolCall` 和 `ToolResult`，再为不同厂商编写适配器。

### 第 2 题

**问题：**

OpenHands 的状态机设计有什么优缺点？更优雅的实现方式是怎么样的？

#### 答案

这道题通常分析的是 OpenHands V0 的 `AgentState + Controller`。它用一个状态值控制 Agent 是否继续运行，适合早期的串行执行；当暂停、确认、限流和异步结果可能同时出现时，单一状态就很难保存完整情况。

##### 1. 优点：简单，容易控制

Controller 只需要判断：

```text
状态是 RUNNING → 执行下一步
其他状态       → 暂时停止
```

这种设计的好处很直接：

- 执行循环容易理解；
- 前端可以直接显示当前状态；
- 状态方便记录和持久化；
- 串行任务出错时比较容易排查。

##### 2. 缺点：一个字段承担了太多职责

旧版 `AgentState` 混合了几类信息：

```text
RUNNING、PAUSED            → 当前是否运行
AWAITING_USER_CONFIRMATION → 正在等待什么
USER_CONFIRMED             → 刚刚发生了什么
FINISHED、ERROR            → 最终结果是什么
```

这些信息可能同时成立。例如，任务可以既处于暂停状态，又在等待用户确认。单一枚举只能保留一个值，另一部分信息就需要额外保存。

如果继续增加 `PAUSED_AND_WAITING_CONFIRMATION` 之类的组合状态，暂停、确认、限流和工具等待会产生越来越多的组合，维护成本会迅速增加。

`USER_CONFIRMED` 也更像一次事件，而不是需要持续保存的状态。把事件放进状态枚举，会增加短暂的中间状态，进程在这里崩溃时也更难恢复。

##### 3. 改进：把不同信息拆开保存

状态机可以继续使用，但 Runtime 内部改成组合状态：

```text
phase：任务仍在进行，还是已经结束
paused：是否暂停
blockers：继续执行前还在等待哪些条件
pending_actions：哪些操作等待执行
outcome：最终成功、失败或取消
```

例如，暂停并等待确认可以同时表示为：

```text
phase = ACTIVE
paused = true
blockers = { USER_CONFIRMATION }
```

用户恢复任务后，只修改 `paused`。此时确认条件还在，所以 Agent 不会错误地继续执行。

用户确认、恢复、工具完成等信息作为事件，按顺序进入统一的转换函数：

```text
新状态、后续动作 = transition（当前状态，收到的事件）
```

前端展示的 `RUNNING`、`WAITING`、`PAUSED` 和 `ERROR`，再根据内部状态计算出来。这样既保留了原设计简单直观的优点，也避免了组合状态越来越多的问题。

#### 解题思路

看到这道题，我会先看 `AgentState` 到底控制了什么。

旧版 Controller 只有在状态为 `RUNNING` 时才执行下一步。一个字段同时服务于执行循环、前端展示和任务恢复，所以早期这样设计很合理：代码少，运行路径也容易理解。

接下来沿着一次确认操作往下看：

```text
等待用户确认
→ 用户确认
→ USER_CONFIRMED
→ 执行操作
→ 回到 RUNNING
```

这里出现了第一个问题。`USER_CONFIRMED` 描述的是用户刚刚做出的操作，它只发生一次，不需要长期保持。把它保存为状态，Controller 就要再增加一步，把这个临时状态转换成运行状态。

然后再加入暂停：

```text
Agent 正在等待确认
用户点击暂停
```

此时有两个事实同时成立：

```text
任务已经暂停
任务仍在等待确认
```

单一枚举只能选择其中一个。增加一个组合状态可以处理这次情况，但后面还有暂停与限流、暂停与工具等待、确认与工具完成等组合。继续穷举下去，状态数量会越来越多。

所以问题的根源并不只是状态数量多，而是不同性质的信息被放进了同一个字段。

改进时，我会先拆开 Runtime 必须回答的几个问题：

```text
任务是否还在进行？
用户是否暂停了任务？
继续执行还缺少什么条件？
有哪些操作正在等待处理？
任务最终怎样结束？
```

这些信息分别保存后，不需要提前列出所有组合。所有外部输入仍然通过事件进入系统，同一个 Session 的事件按顺序处理，再由统一的 `transition` 函数修改状态。

```text
用户消息、确认、暂停、工具结果
              ↓
        统一转换函数
              ↓
        完整 Runtime 状态
          ↙          ↘
 决定能否继续执行    计算前端显示
```

这样设计仍然是状态机，只是内部状态能够表达多个同时成立的事实。事件负责推动变化，状态负责记录当前情况，转换函数负责保证处理规则一致。
